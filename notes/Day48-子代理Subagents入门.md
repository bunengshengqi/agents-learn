## 一、一句话理解子代理

> **子代理就是：主代理（父代理）临时招募的小弟，专门替它去完成某一块子任务。**

每个小弟都有自己的"工位"——独立的上下文窗口、工具权限、执行限制。干完活后，小弟把结果汇报给父代理，父代理再把这些结果汇总成最终答案。

**生活类比**：你是项目经理（父代理），手下有几个实习生（子代理）。你不需要自己把所有文档看完、所有代码写完，而是把任务分包出去，最后整合大家的产出。

---

## 二、为什么需要子代理？单代理的瓶颈

单一 agent 反复面临几类问题：

| 问题 | 通俗解释 |
|---|---|
| **上下文窗口爆炸** | 让它读 10 个文件、20 篇文档，它就像人一样"看迷糊了"，前后文装不下 |
| **明明可以并行却串行做** | 收集销售数据、整理 GitHub PR、汇总用户反馈，三个活互不相关，单代理只能一件一件来 |
| **被要求样样精通** | 一个 agent 既要懂前端、又要懂后端、还要懂数据库设计，容易样样通样样松 |
| **不同任务互相干扰** | 无关的推理链混在一起，前面想的会影响后面判断 |
| **一崩全崩** | 某个子环节出错，整个工作流都挂掉 |

子代理就是针对这些痛点设计的：**把大任务切成小块，让专门的小代理并行处理。**

## 三、子代理的 5 个典型使用场景

### 场景 1：资料爆炸型任务（Research-Heavy Tasks）

**什么时候用**：需要读 **10+** 个文件或文档时。

**例子**：让你总结一个系统的整体架构。

- 子代理 A：读后端代码/文档，总结后端架构
- 子代理 B：读前端代码/文档，总结前端架构
- 子代理 C：读数据库文档，总结数据模型

然后父代理把 A、B、C 的总结拼成一份完整的架构 overview。

**好处**：每个子代理只专注一小块，不会因为信息太多而"失忆"。

---

### 场景 2：多个互相独立的任务（Multiple Independent Tasks）

**什么时候用**：有 **3+** 个互不依赖的子任务时。

**例子**：准备一份产品发布报告。

- 子代理 A：去收集销售指标
- 子代理 B：去整理 GitHub 上的新功能列表
- 子代理 C：去收集用户反馈

这些工作本来互相不依赖，可以同时进行。原本串行做可能要 4 小时，用子代理并行可能只要 2 小时。

**好处**：节省时间，真正"多核并行"。

---

### 场景 3：独立审查 / 第二双眼睛（Fresh Perspective Verification）

**什么时候用**：你需要一个不带偏见的人来检查你的工作。

**例子**：一个子代理负责实现支付系统，另一个**只读**子代理独立审查代码，专门找 bug 和安全问题。

关键是：审查代理不知道实现时代理是怎么想的，所以更容易发现"想当然"的漏洞。

**好处**：自己检查自己的代码很容易"视而不见"。

---

### 场景 4：提交前验证（Pre-Commit Verification）

**什么时候用**：代码合并前要做独立验证。

**例子**：一个子代理写代码，另一个只读子代理在 commit/PR 前做安全审查，防止有问题的代码进入仓库。

**好处**：相当于给代码加了一道质量门槛。

---

### 场景 5：流水线型工作（Pipeline Workflows）

**什么时候用**：任务有明显的前后阶段。

**例子**：开发一个 API。

- 阶段 1：设计子代理设计 API 方案
- 阶段 2：实现子代理基于方案写代码
- 阶段 3：测试子代理基于代码写测试

每个阶段有独立的上下文窗口，不会让"设计时的纠结"干扰"写代码时的专注"，也让后面的代理能更严格地审查前面阶段的输出。

**好处**：复杂工程天然分阶段，子代理让这种阶段划分变得清晰。

---

## 四、什么时候该考虑用子代理？

当你心里出现以下任意一种念头时，就是该上子代理的信号：

- "我需要读 **10+** 个文件才能理解这件事"
- "我要做 **3+** 个互相独立的工作"
- "我想要一个第二意见 / 独立审查"

这些信号其实就是前面 5 个场景的简化版。

## 五、子代理的优势

- ✅ **并行执行**：多个任务同时进行
- ✅ **独立上下文**：每个子任务有自己的"记忆空间"，不会互相污染
- ✅ **专业工具**：不同子代理可以配备不同工具
- ✅ **失败隔离**：一个子代理崩了，其他还能继续
- ✅ **扩展性好**：加更多子代理不会拖垮父代理
- ✅ **任务分解**：把复杂大任务自然拆成可管理的小块

## 六、什么时候不要用子代理？

| 不适合的情况 | 原因 |
|---|---|
| **强串行依赖** | 任务 B 必须等任务 A 的输出，并行不起来 |
| **同时编辑同一个文件** | 多个子代理改同一个文件，会造成 Git 冲突 |
| **任务本身很小** | 创建子代理有开销，小题大做不划算 |
| **需要超过 5 个专业代理** | 协调成本太高，反而混乱 |

**核心原则**：子代理是用来解决"复杂、可分解、可并行"的问题的，不是用来炫技的。

## 八、一句话总结

> **子代理的本质，就是"分而治之"：把一件大事拆成多件小事，让多个专门的小 agent 并行做，最后汇总结果。**

它不是为了把简单问题复杂化，而是为了在任务太大、信息太多、需要并行或需要独立审查时，让 agent 系统更有条理、更可靠、更高效。

## 九、今日面试题

**Q：什么时候应该使用子代理（Subagents）？请举两个实际例子。**

**参考答案要点**：

1. 当任务需要读取 10+ 个文件或文档时，可以将不同文档分给不同子代理并行阅读，最后由父代理汇总。
2. 当需要独立审查时，可以让一个子代理负责实现，另一个只读子代理独立审查代码，避免"自我盲区"。
3. 使用子代理的核心判断标准是：任务是否复杂、是否可分解、是否有独立或并行的需求。
